2. Executive Verdict

Updated after approved research

Recommendation: hold an actively supported controlled OSS preview until five proof gates close.

Chromux is no longer a feasibility prototype. The current checkout is a feature-rich Electron app with source and packaged commands, macOS and Windows/WSL2 routes, paired sessions, approval-gated previews, local capture persistence, live-session Composer routing in the current 0.64.0 candidate, troubleshooting and privacy docs, an issue-form draft, many regression fixtures, and a passing smoke check.

The missing evidence is adoption evidence: clean Apple Silicon reproduction, three voluntary sessions in seven days, a durable localhost/capture artifact, observed recovery, and one non-builder self-serve success.

Important distinction: the source repository is already public. “Controlled OSS preview” means an invited and supported cohort on a named immutable candidate—not making the code visible.

5. Three Adoption Loops

Loop A — Builder Daily-Driver

Trigger: a real task needs terminal-native coding agents and a localhost or local HTML review surface.

  1. Start, resume, detect, or adopt a Claude Code, Codex, Grok Build, or shell session.
  2. Produce a loopback URL or local HTML path.
  3. Confirm the originating queue receives the preview without stealing attention.
  4. Approve and inspect it.
  5. Capture or attach bounded evidence.
  6. Route through the intended live session in the candidate or use the inspectable fallback.
  7. Record response usefulness and voluntary return.

Activation: one real task completes approved preview → bounded evidence → inspectable routing → actionable response. Retention: three real sessions in seven days. Failure: returning to terminal plus external Chrome because Chromux is slower or less trustworthy.

Loop B — Reproducibility And Proof

  1. Select one immutable commit or tag.
  2. Run clean Apple Silicon setup from public docs.
  3. Start the durable localhost fixture.
  4. Complete the preview/capture/response loop.
  5. Exercise one recoverable failure.
  6. Archive commands, timing, screenshots, payload references, errors, recovery, and result.
  7. Fix only observed friction and rerun.

Activation: complete archived proof packet. Retention: later candidates preserve the verification contract. Failure: undocumented maintainer knowledge or destructive workaround is required.

Loop C — Controlled OSS Preview

  1. Invite one matching non-builder with immutable target, prerequisites, privacy boundary, and supported scenario.
  2. Require one first-success scenario without synchronous help.
  3. Collect the structured report and redacted recovery evidence.
  4. Classify install, preview, capture, routing, response, docs, or trust failure.
  5. Convert blockers into repo work without broadening acquisition.
  6. Hold, repeat with one person, or graduate to a small cohort.

Activation: one non-builder self-serves. Retention: they return or provide another attributable usage report. Failure: rescue, wrong-session/data-loss, or no safe recovery path.

6. Activation Path And Decision Rules

First-success contract

  1. A supported candidate launches.
  2. A real agent or shell session runs in the intended project.
  3. A real localhost URL or local HTML path is detected or explicitly opened.
  4. The browser opens only after approval.
  5. Bounded evidence persists and visibly associates with the intended target.
  6. The agent produces an actionable response, or the fallback leaves an inspectable artifact and exact retry path.

Opening the app, opening a pane, running a regression, producing a screenshot, or sending a prompt alone is not activation.

RecoveryArtifacts preserved and documented action succeedsLoss, opacity, or undocumented rescue

No threshold is yet set for time-to-first-success, useful-capture rate, or retry rate. Record a baseline before defining “good.”

10. Distribution And Trust Boundary

The current macOS source install is unsigned. Apple says Developer ID signing lets Gatekeeper verify software distributed outside the Mac App Store, while notarization scans Developer ID-signed software and supplies a Gatekeeper ticket.

  • A clean source-build record can test the approved technical cohort when the unsigned/source boundary is explicit.
  • If a downloaded app, DMG, PKG, or ZIP becomes the supported route, signing, hardened-runtime compatibility, notarization, and first-launch testing enter the reproducibility gate.
  • Signing/notarization is distribution trust evidence, not product-value evidence.
  • Universal binaries, cross-platform packaging, enterprise deployment, and procurement stay outside this run.

17. Rejected Or Lower-Confidence Findings

  • Rejected: release count proves retention; it proves maintainer activity.
  • Rejected: zero stars/issues means no demand; repo is new, traffic uninspected, and counts do not measure activation.
  • Rejected: issue form proves readiness; it proves support-field design and is unpublished/unused.
  • Rejected: localhost fixture is complete; tests prove listeners/detection/readiness/queueing, not a preserved page/capture/response artifact.
  • Rejected: signing must precede founder proof; it matters for downloaded binary trust.
  • Lower confidence: live-session Composer materially improves retention; it is fresh candidate behavior.
  • Lower confidence: one participant represents broader OSS; it is a directional gate, not a market estimate.
  • Lower confidence: first cohort should stay macOS-only after Windows/WSL2 support; this is approved scope, not a market conclusion.
