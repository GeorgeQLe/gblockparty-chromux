Assumptions manifest

Choose confirm, correct, or flag for every assumption. Correct and flag reveal a note field.

1. Product identity and wedge

[from repo] Chromux is an OSS macOS Electron/Chromium desktop cockpit for local and optionally GBlockParty-managed agent/browser workspaces; its adoption wedge is parallel terminal-native coding sessions paired with inspectable browser previews and bounded evidence capture.

2. Primary audience and buying context

[from research] The current priority audience is a technical solo builder already using Claude Code, Codex, or Grok Build on Apple Silicon macOS. Team buyers, procurement, and enterprise administration are later conversion contexts, not the current activation target.

3. Product maturity

[from repo] Chromux is beyond prototype feasibility: current metadata is version 0.61.8, the repository has a source quickstart and release/update path, and numerous workflow regressions are scripted. Adoption evidence should therefore focus on reproducibility, real repeated use, and external first success—not whether an app exists.

4. Available outcome evidence

[from repo] The repository proves mechanisms and configured-machine workflows, but it does not currently contain completed daily-driver metrics, clean-machine observation, attributable external user reports, or measured retention outcomes.

5. Near-term constraints and non-goals

[from research] The near-term adoption plan should not optimize broad launch, paid packaging, team rollout, cross-platform support, or forced telemetry before the solo-builder journey is reproducible and repeated-use evidence exists.

6. Riskiest adoption assumption

[inferred] The riskiest current assumption is that the session-paired cockpit and evidence-capture loop create enough recurring value to make a developer choose Chromux over their existing terminal-plus-browser workflow after novelty wears off.

7. Disposition of the unfinished July packet

[from repo] The 2026-07-06 Stage 2 packet should be treated as historical background and reconciled into this new run only after current scope approval; it should not be approved unchanged.

1. What decision should this adoption research make possible, and over what time horizon?

Agent confidence: medium
Recommended: produce a 30–60 day proof-led adoption plan that decides what must be demonstrated before a controlled OSS preview, while keeping broad launch out of scope.
Use a 30–60 day decision horizon. The report should define the evidence and artifacts required to move from the current solo-builder daily-driver stage to a controlled OSS preview, while keeping broad public launch outside this run.

2. What should count as activation, first success, and retention for this run?

Agent confidence: medium
Recommended: activation is completing one real session-paired preview/capture/handoff loop; retention is choosing Chromux for at least three real sessions in a week; preview readiness additionally requires one non-builder to complete first success without synchronous help.
Activation: complete one real coding task with a paired agent session, approved browser preview, bounded evidence capture, inspectable handoff, and an actionable agent response. Retention: choose Chromux for at least three real sessions in seven days. Controlled-preview readiness: one non-builder completes the documented first-success loop without synchronous help.

Recommended: prioritize a clean-machine install record, a real localhost first-success fixture, a failure-recovery transcript, a daily-driver observation template, and a controlled-preview first-success form. Add or remove proof requirements based on what would change your decision.
