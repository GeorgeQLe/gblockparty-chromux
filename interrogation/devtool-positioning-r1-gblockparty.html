Why this is a new research fork

The canonical Chromux positioning report is product-local. It frames Chromux against terminal-plus-browser workflows, AI coding surfaces, and browser automation tools. The repository now also describes Chromux as a front end for optional GBlockParty-managed workspaces, but the GBlockParty control plane is explicitly architectural—not yet an implemented service in this checkout.

Scope evidence, not a finding: the requested “overall GBlock Party competitive analysis” changes the unit of competition from one desktop app to a possible product system. Before researching, the skill needs the intended GBlock Party portfolio boundary and the strategic role Chromux should play within it.

Assumptions manifest

Choose confirm, correct, or flag for every assumption. Correct and flag reveal a note field.

1. Product-system boundary

[from repo] For this run, GBlock Party is provisionally treated as a developer-workspace system: Chromux owns the local cockpit and attachment experience, while a future GBlockParty control plane owns managed workspace lifecycle, persistence, events, access, and optional hosted execution.

2. Chromux’s strategic role

[from repo] Chromux should be evaluated both as a standalone local-first product and as the user-facing wedge into optional GBlockParty-managed infrastructure; connecting an account should extend the same workspace model rather than replace the local workflow.

3. Audience sequence

[from research] The starting user is still an agent-driven developer who values local control. Teams, platform owners, security stakeholders, and managed-infrastructure buyers are secondary audiences whose needs matter to the portfolio frame but should not overwrite the current individual workflow.

4. Uneven maturity must remain visible

[from repo] The analysis must distinguish shipped Chromux capabilities from proposed GBlockParty services. It should not use the future control-plane design as proof of current market capability or make trust, scale, collaboration, or hosted-execution claims without evidence.

5. Competitive analysis needs layered alternatives

[inferred] A useful overall analysis should compare workflows and substitutes across at least four lanes: local AI development environments, cloud/remote developer workspaces, autonomous agent platforms, and browser/runtime infrastructure—plus doing nothing or assembling the stack in-house.

6. Riskiest positioning assumption

[inferred] The riskiest assumption is that “local cockpit plus optional managed workspace continuity” forms a coherent category wedge rather than reading as two loosely connected products with stronger specialists on each side.
